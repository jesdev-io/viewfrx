# `frxview`: A lightning fast audio file browser

## Goal
The goal of this app is to be a vibe-coded, backed-by-reference, super fast, compact, easy to use app for browsing and listening to audio files (`.wav`, `.mp3`, ...) written in **rust**. Why is this needed? Because in scenarios where lots of data is browsed according to human metrics such as personal taste, speed is key: Imagine a gignatic database of field recordings or foley sounds. To find a fitting audio scene, a human curator needs to be able to quickly get the gist of the sound both in terms of technical and meta data and in feel. The second can be provided by super fast, immideate playback and super responsive jumps along the audio file, proper speed-up implementation and an overall snappy feel.

## App windows
The App does not need much. But what it has, should be concise and fast. Audio files or folders can be imported, only audio files are shown if a folder is selected. This file browsing window is to the left. Metadata is shown in the upper center, while the rest of the middle row has space for the audio waveform, the audio control buttons and the timeline in general, where the play bar is located. To the right, there are playback settings and a live VU meter and a configurable magnitude spectrum. Additionally, a spectrogram can be shown above the timeline if needed, similar to audacity. Gain can be manipulated for playback and metadata can be added if desired. For any controllable parameters add a "double click to reset" feature: double clicking modified gain will reset the gain back to 1 (or 0 dB). Audio metrics should be renderd professionally, meaning in dB(FS) and vertical stereo VU meter. Provide an auto-scale gain with the following behavior: the original waveform is shown. Behind it, an auto-scaled version of it is shown in a less prevalent color. This helps outlining the level behavior in time domain. A toggle button "Normalize" can be enabled to play back the sound with that shown auto gain of the less pronounced waveform. It should behave like the Audacity "Normalize" where the peak value of the waveform is at -1 dBFS after normalization. Give the buttons fitting symbols instead of strings: "play" is a triangle, "pause" two vertical lines. The app should be able to show both tracks left and right. A small selection should show "Left", "Right" or "Both", same is true for the spectrogram. This of course only makes sense for actual stereo recordings. The waveforms and spectrograms should be grouped visually, so they are displayed as "wave L", "wave R", "spec L", "spec R" and not shuffled. In settings, one can enable a debug window with the console messages piped through to better understand the process. Both waveforms and spectrogram should have modifiable heights by dragging their edges downward and upward. They should also have a zoom feature where a subsection then takes up the entire available width. Zoom can be performed via two zoom in and zoom out buttons or scrolling when hovering over the spectrogram or waveform. All time data scales in tandem when zoomed: all waveforms, all spectrograms.

## Performance
To ensure good performance, we need proper caching and preloading. The worst that can happen is for the app to be laggy or freeze. This is not allowed to happen. Some form of multithreading is mandatory. The system's audio devices and drivers need to be recognized and should be configurable in the settings. Choose and audio backend that will be supported and used in the coming years, don't pick an EOL audio backend. Always analyze the following metrics: How big is the program build? How much RAM does it eat? What about audio latency? These shall not be abnormal. Accidentally importing several GB of data shall not result in a RAM deadlock of the entire system.

## DSP
Besides proper gain scaling, dynamic playback rate and a spectrogram, not much DSP is needed. However, the app should be able to deal with "anomalous" audio files, for example, with a DC offset. This influences the gain scaling in an unintuitive way. Remove all DC offset, but list it as a file parameter in dB. Audio might come in very raw, meaning it cannot be assumed that the recording device provided any kind of clever filtering. The most important thing is a short onset/offset gain fade, otherwise the start and stop of a recording produce a nasty dirac-pop when played back. A fixed highpass should also be added as a toggle feature to get rid of possible infra-sound content.

## Project
Use git locally here. A remote has not yet been set up, this will come later. Try to target linux, windows and macos. Be sure that the code does not contain any magic numbers. If such numbers exist, due to, for example, GUI spacing, put them into their own config block/file. It is important that this software is, except for a "recently opened" suggestion, stateless. It shall not keep any information of prior sessions; a "session" is just defined by a folder's contents; that's it. If possible, users should be able to annotate recordings with timestamps which can then be saved to file metadata in a way that does not harm the file; it should still be a normal audio file that any player can open. The way to do that is via a text field at the bottom that follows a "[dd:hh:mm:ss]" free-text format. This will automatically create a timestamp in that recording for that time shown as a vertical line in the waveform. One can also right-click at a time position and create an annotation there. Both methods are idempotent and render each other. Important: this operation modifies the audio files. As long as a recording is selected and viewed, any new timestamps should be floating. By saving the file via the menu or Ctrl+S, a save dialog is opened that operates the standard way of naming a file and a warning if the same filename is used. That way, annotations can intentionally be saved by a user. If another file is opened, a warning should remind the user of unsaved annotations. These can then either be dismissed (= annotation is lost) or saved as mentioned before. Of course, annotations should be rendered if they were found on a file. Of course, annotation read/write has to work via the CLI as well.

## Key to success
ArtCraft is so succesful because it exposes everything in the app as CLI. DO the same. This way, you can write unit tests. test, test, test. A test fails? Dont just hardcode the test to succeed. Check what caused the issue in the first place. Keep the codebase tight. Reuse code. Test. Run. Check speed performance. Check responsiveness. A sold CLI indicated that we are 90% of the way there. Do not crate spaghetti code where backend and frontend are mixed. The program has to run entirely on CLI, only then can we create a UI layer on top of that. The main CLI commands can be exported as a classic top bar menu.
